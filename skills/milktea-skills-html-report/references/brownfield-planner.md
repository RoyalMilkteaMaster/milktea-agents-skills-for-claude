# 既有系統重構規劃：架構健檢決策報告

## 用途

在實作前，讓使用者判斷「要不要重構、應該採用哪個方案」。

## 產生時間

完成唯讀架構盤點後，產生 Spec 與 Tickets 之前。

只有呼叫者識別為 brownfield-planner，而且 Architecture Auditor 已交回完整盤點證據時才能產生。盤點開始時即沿用 Planner 建立的唯一工作識別碼，固定寫入 `docs/architecture-reviews/<工作識別碼>/architecture-review.html`；同一次盤點修改時更新同一份報告，不以日期或範圍名稱共用檔案。

驗證時傳入 `--project-root <專案根目錄> --work-id <工作識別碼>`；HTML 根元素的 `data-work-id`、目錄名稱與傳入值必須完全一致。

## 首頁先回答

- 這個專案是做什麼的。
- 本次檢查範圍。
- 是否值得重構。
- 推薦哪個方案。
- 最大三項風險。
- 使用者現在需要做什麼決定。

## 報告主要內容

### 現況摘要

- Code／Data／Runtime Root。
- 專案主要入口、模組與實際使用流程。
- Git SHA、工作樹狀態、檢查範圍與排除範圍。
- 已確認、推論、未知及未驗證的範圍，四者必須分開顯示。

### 現況架構與資料流

- 目前模組之間的關係。
- 資料由誰擁有、誰讀取、誰修改、最後流向哪裡。
- 主要公開介面、共用 API、服務、元件及使用位置。
- 循環依賴、共享狀態、隱性副作用及高風險共用水管。
- 正式 Logging 只在現有規則判定需要時說明；不需要時只寫結論及理由。

### 問題與清理候選

- 重複、過度分層、廢棄、錯放或用途未知的內容。
- 每個候選都要列出實際位置、判斷證據、可能影響與回復方式。
- 清楚標示建議是保留、合併、封存、重建、移除候選或仍然未知。
- 搜尋不到引用只能列為候選，不能直接判定刪除。
- 無法排除動態載入、外部工具、人工流程或未提交工作時，必須標示未知。

### 改善方案

- 比較保留現況、局部整理、合併、封存及局部重建。
- 說明每個方案能改善什麼、需要改多少、主要代價、風險與回復方式。
- 推薦一個方案，並說明推薦理由及什麼情況下不適用。
- 顯示候選目標架構、目標目錄、模組責任、資料所有權與遷移順序。

### 相容性與決策

- 必須保留的原有功能。
- 每項原有功能在修改前的驗證方法與通過標準。
- 相容性風險、資料風險、回復方式及仍待使用者決定的事項。
- 最後提供三個選擇：只保留報告／繼續規劃／修改報告。

## 視覺風格

- 定位是「專業架構稽核報告」。
- 主色使用深藍、石板灰及琥珀色警示。
- 首頁像管理層摘要，不像技術文件。
- 左側或頂部提供精簡目錄。
- 重要結論使用大卡片。
- 技術證據、完整路徑與命令預設收合。
- 不使用綠色「完成」、成果慶祝或已改善語氣，因為尚未實作。

## 聊天框

只顯示 HTML 報告連結，以及「只保留報告／繼續進入 to-spec／修改這份報告」三個選項，不重述報告內容。
