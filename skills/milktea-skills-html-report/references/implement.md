# 功能實作：功能完成驗收報告

## 用途

所有工作做完後，告訴使用者「實際完成了什麼、改善多少、是否符合一開始提出的要求」。

## 產生時間

所有 Tickets、測試、Review、修正、定向複驗與最終總驗收全部完成後，只產生一次。

只有呼叫者識別為 implement，而且整個 Task 沒有執行中、Review 中、修正中、受阻或未完成的 Ticket 時才能產生。固定寫入 docs/work/功能名稱/completion-report.html。

單張 Ticket 完成、單次 Review、修正或複驗時都不能產生或更新 HTML。

## 首頁先回答

- 最終驗收是否通過。
- 使用者一開始提出的要求完成幾項。
- Tickets 完成數量。
- 測試通過數量。
- 最重要的改善數據。
- 是否還有未完成項目；沒有就直接顯示「全部完成」。

## 報告主要內容

### 原始要求完成狀態

先完整列出使用者一開始提出的所有要求，不能只列 Spec 標題或由 Agent 自己改寫成模糊摘要。

每項要求都要顯示：

- 原始要求。
- 完成狀態。
- 實際完成結果。
- 驗收證據。
- 若不是完成，說明原因、影響及下一步。

狀態只能使用：

- 完成：要求已實作並通過驗收。
- 部分完成：只完成其中一部分，必須明確指出完成與未完成的部分。
- 未完成：仍未交付或未通過驗收，必須說明原因與影響。
- 範圍外：本次核准範圍原本就不包含這項內容，必須說明判定依據。

如果所有原始要求都是「完成」，在本區最上方明確顯示「全部完成」。

### 實際修改內容

- 這次實際做了什麼。
- 改了哪些檔案、模組、介面、資料結構或設定。
- 每項修改解決哪一個原始要求。
- 修改後使用者實際會看到或感受到什麼變化。
- 額外發現與範圍外修改分開顯示：
  - 額外發現：實作時發現但不屬於原始要求的問題，說明是否處理及理由。
  - 範圍外修改：若實際修改超出核准範圍，列出修改內容、必要性與使用者授權證據；沒有就寫「沒有範圍外修改」。

### 架構與資料流前後對比

- 修改前架構。
- 修改後架構。
- 哪些模組責任改變。
- 資料流如何變化。
- 公開介面、資料所有權或外部整合是否改變。
- 實際結果是否偏離原本規劃；有偏離就說明原因、影響及核准證據，沒有就寫「實際結果符合原規劃」。

### 改善數據

每個改善指標都要列出：

- 指標名稱。
- 修改前數值。
- 修改後數值。
- 差值與百分比。
- 單位。
- 計算方式。
- 證據來源。

可以使用測試數量、執行時間、人工步驟、依賴數、警告數、覆蓋率或其他實際測得的指標。沒有修改前基準時，直接寫「無法量化：缺少修改前基準」，不能自行估算或編造數字。

### 最終驗收

- 每項測試與驗收的名稱、實際指令或方法、結果及退出碼。
- Reviewer A／B 各自的最終結論。
- Findings 提出、修正、反駁、關閉或撤回的摘要。
- 未完成事項：
  - 列出對應的原始要求、未完成原因、實際影響及完成它需要的下一步。
  - 沒有未完成事項就明確寫「全部完成」。
- 未解風險：
  - 說明風險是什麼、什麼情況會發生、會影響什麼及目前如何降低風險。
  - 沒有已知未解風險就寫「沒有已知未解風險」。
- 回復方式：
  - 說明什麼情況需要回復、要還原哪些程式或資料、實際步驟及回復後如何驗證。
- 人工下一步：
  - 說明由誰、在什麼情況、執行什麼操作，以及預期看到什麼結果。
  - 沒有人工下一步就寫「不需要人工處理」。

只有實際證據足以支持時才畫圖；不能為了好看製造完成率或改善數字。

## 視覺風格

- 定位是「產品交付成果與驗收儀表板」。
- 主色使用深綠、海軍藍與白色。
- 首頁直接顯示成果與通過狀態。
- 大量使用前後對比卡與可驗證的量化數字。
- 每張 Ticket 的模型、推理強度及詳細 Review 紀錄預設收合。
- 不在聊天框重貼內容，只提供驗收狀態與 HTML 連結。

## 聊天框

只顯示「最終驗收通過」及 HTML 報告連結，不逐票重述執行與 Review 資料。
