# 需求規劃與拆票：實作藍圖核准報告

## 用途

在實作前，讓使用者確認「需求、架構與 Tickets 是否拆得正確，可以開始派工嗎」。

## 產生時間

需求、架構、Spec 及全部 Tickets 都完成後，建立執行 Task 之前。

只有呼叫者識別為 grill-me，而且需求覆蓋、依賴、並行、寫入所有權、角色與驗收資料全部齊全時才能產生。固定寫入 docs/work/功能名稱/implementation-plan.html；規劃修改時更新同一份報告。

## 首頁先回答

- 這次要做什麼。
- 預期完成後會得到什麼。
- 有幾張 Tickets。
- 哪些 Tickets 可以安全並行。
- 最長依賴路徑。
- 有哪些風險或待核准事項。
- 是否建議開始實作。

## 報告主要內容

### 原始需求與範圍

- 使用者一開始提出的要求。
- 每項要求的驗收條件。
- 明確不處理的範圍。
- 每項需求由哪張 Ticket 負責。
- 沒有被任何 Ticket 覆蓋的需求必須直接標示，不能假裝規劃完整。

### 目標架構與資料流

- 準備新增、修改、搬移或移除哪些模組。
- 修改前架構與預計修改後架構。
- 新的資料流、公開介面與資料所有權。
- 各模組的責任及彼此怎麼連接。
- 相容性、Migration 與舊資料如何處理。

### Ticket 執行藍圖

- 每張 Ticket 的目標、使用者價值與可驗證交付結果。
- Ticket 之間的依賴與阻擋關係。
- 建議執行順序。
- 可以安全並行的批次，以及不能並行的實際原因。
- 每張 Ticket 的寫入所有權與共用資源鎖。

### Agent 與驗收設計

- 每張 Ticket 的 Developer 配置及選擇理由。
- Reviewer A／B 各自負責什麼。
- 每張 Ticket 的測試接縫、完整驗收方式及必交證據。
- Findings 如何交回原 Developer 修正或反駁，以及如何由原 Reviewer 定向複驗。
- 模型與推理設定只顯示影響執行的摘要，完整設定預設收合。

### 風險與核准

- 相容性、資料、Migration、共用資源、寫入衝突與執行環境風險。
- 每項風險會影響什麼、如何避免，以及需要回復時怎麼做。
- 尚未解決、必須由使用者決定的事項。
- 最後提供三個選擇：核准實作／修改規劃／暫停。

## 視覺風格

- 定位是「工程藍圖與派工控制台」。
- 主色使用靛藍、藍紫與青色。
- 背景可以有淡淡的工程格線感。
- Ticket 使用有編號的卡片與依賴線。
- 執行順序使用時間線或泳道呈現。
- 所有用語使用「預計、規劃、將會」，不能假裝已經完成。
- HTML 取代聊天框中的長篇 Ticket 規劃；聊天框只放連結與核准選項。

## 聊天框

只顯示 HTML 報告連結，以及「核准實作／修改規劃／暫停」三個選項。使用者核准後才顯示唯一的執行 Task 交接內容。
