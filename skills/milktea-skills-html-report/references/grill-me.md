# 需求規劃與拆票：實作藍圖核准報告

## 用途

在實作前，讓使用者確認「需求、架構與 Tickets 是否拆得正確，可以開始派工嗎」。

## 產生時間

需求與架構已確認、Spec 已核准，而且全部 Ticket 草稿文件內容已填完整後；此時尚未開始實作，也不能把 Ticket 標為「完成」。

只有呼叫者識別為 grill-me，而且需求覆蓋、依賴、並行、寫入所有權、角色與驗收資料全部齊全時才能產生。新工作固定寫入 `docs/work/<工作識別碼>/implementation-plan.html`；舊工作沿用實際交接工作目錄。規劃修改時更新同一份報告。

## 機器驗證閘門

- 必須使用 `scripts/validate_report.py <報告路徑> --caller grill-me --project-root <專案根目錄> --work-id <工作識別碼>`，不可省略專案根目錄或工作識別碼。
- 新工作識別碼必須符合 `wp-YYYYMMDD-HHmmss-xxxxxxxx`，固定路徑為 `docs/work/<工作識別碼>/implementation-plan.html`，HTML 根元素的 `data-work-id` 必須完全一致。
- 舊工作可沿用 `docs/work/<實際舊目錄名稱>/implementation-plan.html`，把該目錄名稱原樣傳入 `--work-id`；不搬移、不改名。
- Spec 文件前言的 `工作識別碼` 與 `狀態` 必須各自在前言和全文件恰好出現一次，`狀態` 精確為「已核准」。
- Spec 的「原始需求」必須使用唯一 `R-xxx` 與原文。每張 Ticket 必須保留相同原文，且全部 Spec R-ID 至少由一張 Ticket 覆蓋；HTML 的「原始需求與範圍」也必須逐字顯示每個 R-ID 與原文。
- 至少要有一張真正完整的 Ticket；每張 Ticket 的 `狀態` 必須只在文件前言及全文件各出現一次，且精確為「草稿」。Ticket 標題、To-ticket 契約既有的必要章節、驗收與測試、前端規劃、依賴、Dispatch、寫入所有權、共用鎖、初始執行配置、Agent 分工及預建執行欄位都必須存在；規劃階段應決定的內容不能留空或保留選項占位。任何 Ticket 已核准、執行中、完成或只是空殼時，都不能產生這份實作藍圖。

## 首頁先回答

- 這次要做什麼。
- 預期完成後會得到什麼。
- 有幾張 Tickets。
- 哪些 Tickets 可以安全並行。
- 最長依賴路徑。
- 有哪些風險或待核准事項。
- 是否建議開始實作。

## 報告主要內容

### 原始需求與範圍

- 使用者一開始提出的要求。
- 每項要求的驗收條件。
- 明確不處理的範圍。
- 每項需求由哪張 Ticket 負責。
- 沒有被任何 Ticket 覆蓋的需求必須直接標示，不能假裝規劃完整。

### 目標架構與資料流

- 準備新增、修改、搬移或移除哪些模組。
- 修改前架構與預計修改後架構。
- 新的資料流、公開介面與資料所有權。
- 各模組的責任及彼此怎麼連接。
- 相容性、Migration 與舊資料如何處理。

### Ticket 執行藍圖

- 每張 Ticket 的目標、使用者價值與可驗證交付結果。
- Ticket 之間的依賴與阻擋關係。
- 建議執行順序。
- 可以安全並行的批次，以及不能並行的實際原因。
- 每張 Ticket 的寫入所有權與共用資源鎖。

### Agent 與驗收設計

- 每張 Ticket 的 Developer 配置及選擇理由。
- Reviewer A／B 各自負責什麼。
- 每張 Ticket 的測試接縫、完整驗收方式及必交證據。
- Findings 如何交回原 Developer 修正或反駁，以及如何由原 Reviewer 定向複驗。
- 模型與推理設定只顯示影響執行的摘要，完整設定預設收合。

### 風險與核准

- 相容性、資料、Migration、共用資源、寫入衝突與執行環境風險。
- 每項風險會影響什麼、如何避免，以及需要回復時怎麼做。
- 尚未解決、必須由使用者決定的事項。
- 最後提供三個選擇：核准實作／修改規劃／暫停。

## 圖表

- 需求到 Ticket 的覆蓋矩陣。
- 目標架構圖。
- 目標資料流。
- Ticket 依賴圖。
- 並行泳道圖。
- 寫入所有權與風險矩陣。

只有資料足以支持時才畫圖；不能把預估數字當成已完成成果。

## 視覺風格

- 定位是「工程藍圖與派工控制台」。
- 主色使用靛藍、藍紫與青色。
- 背景可以有淡淡的工程格線感。
- Ticket 使用有編號的卡片與依賴線。
- 執行順序使用時間線或泳道呈現。
- 所有用語使用「預計、規劃、將會」，不能假裝已經完成。
- HTML 取代聊天框中的長篇 Ticket 規劃；聊天框只放連結與核准選項。

## 聊天框

只顯示 HTML 報告連結，以及「核准實作／修改規劃／暫停」三個選項。使用者核准後才顯示唯一的執行 Task 交接內容。
