# 共用規則

## 語言

- 所有可閱讀的標題、說明、圖例、狀態與結論使用繁體中文。
- 檔名、指令、模型名稱、程式識別字與必要技術名稱可保留原文。
- 專有名詞第一次出現時，先用中文說明用途。
- 避免連續堆疊英文縮寫與不影響決策的內部設定。

## 事實與證據

- 只使用呼叫者提供的需求、架構、Spec、Tickets、差異、測試、Reviewer、Git 或執行證據。
- 明確區分已確認、推論、候選、未知、未驗證與範圍外。
- 不得捏造修改、測試、Reviewer 結果、完成率或改善數字。
- 每個重要結論都要能追溯到檔案、版本、指令、測試或人工驗收。
- 不嵌入 Token、Cookie、完整環境變數、機密或不必要的個人資料。

## 量化

量化指標必須包含修改前、修改後、差值或百分比、單位、計算方式與證據來源。缺少修改前基準時，明確寫「無法量化：缺少修改前基準」。

圖表只使用真實資料。資料不足時減少圖表，不製造裝飾性數字；重要圖表旁附數值或表格，讓使用者能核對。

## 資訊密度

- 首頁先回答本報告最重要的決策或結果。
- 最上層主要區域不超過五個。
- 一個概念只說一次。
- 長路徑、完整指令、模型設定、原始輸出與逐 Ticket 證據放入可展開區塊。
- 優先使用卡片、對照表、矩陣、流程圖與有數據的圖表，避免長篇散文。
- 有足夠資料時以四至六個有意義的圖表為目標，沒有資料時不硬湊。

## 固定產生規則

- brownfield-planner：只在唯讀架構盤點完成後產生一次；同階段修訂更新原檔。
- grill-me：只在 Spec 與全部 Tickets 完成後產生一次；同階段修訂更新原檔。
- implement：只在整個 Task 的全部 Tickets 與最終驗收完成後產生一次。
- brownfield-implement：只在全部重構 Tickets、原有功能確認與最終驗收完成後產生一次。

任一 Implement 流程尚有執行中、Review 中、修正中、受阻或未完成的 Ticket 時，不產生完成報告。

## 設計輔助標記

報告必須有 id="design-assist" 的欄位，內容依實際情況使用：

- Claude Design
- 內建模板（Claude Design 無法使用）
- 內建模板

不得宣稱使用未實際使用的設計工具。

## 驗證

報告必須使用 UTF-8，根元素標示 lang="zh-Hant"、正確的 data-report-profile 與觸發狀態，並包含專屬規格要求的五個主要 section。

產物不得殘留雙大括號模板欄位、TODO、未替換提示或另一個呼叫者的模板識別。
