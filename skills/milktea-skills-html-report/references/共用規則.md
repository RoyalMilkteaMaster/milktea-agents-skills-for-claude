# 共用規則

## 語言

- 所有使用者可閱讀的標題、說明、狀態與結論使用繁體中文。
- 檔名、指令、模型、程式識別字、通訊協定與必要技術名稱可以保留原文。
- 專有名詞第一次出現時先說明用途，不堆疊無助於決策的英文縮寫。

## 工作識別與相容性

- 新工作使用 `wp-YYYYMMDD-HHmmss-xxxxxxxx` 唯一工作識別碼，實際工作目錄為 `docs/work/<工作識別碼>/`。
- 繁體中文顯示名稱只供閱讀，不作為唯一性或路徑依據，也不得取代原始需求。
- 舊工作使用實際交接的 `docs/work/<功能名稱>/`；不搬移、不改名、不覆寫。
- 同一工作識別碼只允許一份 `progress-report.html`、一份可變的 `completion-report.pending.html` 與一份不可變的 `completion-report.html`。

## 兩頁生命週期

### 進度頁

- Implement 啟動後即可建立 `<實際工作目錄>/progress-report.html`。
- 只讀 Spec、Tickets 與既有執行證據；Ticket 是唯一進度來源。
- 使用 `scripts/progress_server.py` 經 SSE 非同步推送，前端不得輪詢、自動重新整理或整頁重載。
- 進度頁不是完成證明，不得顯示「最終驗收通過」。

### 結案報告

- 全部 Tickets、Review、修正、定向複驗、最終總驗收及適用的原生瀏覽器驗收完成後，先產生 `<實際工作目錄>/completion-report.pending.html`；正式檔此時仍不得存在。
- 必須使用驗證器的 `--candidate --publish` 對候選內容與實際工作目錄一起驗證；全部通過後才原子發布 `<實際工作目錄>/completion-report.html` 並刪除候選檔。
- 正式檔一旦發布即視為不可變結案紀錄，不得覆寫。早產、手動建立或驗證失敗的同名檔不算完成，進度頁與歷史清單也不得顯示為正式結案。
- `implement` 與 `brownfield-implement` 的報告內容由原始需求與實際證據決定；HTML 資產只是彈性排版外殼，不得強迫不適用的專案段落。

## 事實與證據

- 只使用呼叫者提供的需求、架構、Spec、Tickets、差異、測試、Reviewer、Git、原生瀏覽器操作或執行證據。
- 明確區分已確認、推論、候選、未知、未驗證與範圍外。
- 不得捏造修改、測試、Reviewer 結果、瀏覽器操作、完成率或改善數字。
- 每個重要結論都要能追溯到檔案、版本、指令、測試或實際操作證據。
- 不嵌入 Token、Cookie、完整環境變數、機密或不必要個人資料。

## 量化

量化指標必須包含修改前、修改後、差值或百分比、單位、計算方式與證據來源。缺少修改前基準時明確寫「無法量化：缺少修改前基準」，不得估算或編造。

圖表只使用真實資料。資料不足時不硬湊圖表；重要圖表旁附可核對的數值或表格。

## 資訊密度

- 首頁先回答目前進度或最終結論。
- 一個概念只說一次。
- 長路徑、完整指令、模型設定、原始輸出與逐 Ticket 證據放入可展開區塊。
- 優先使用卡片、對照表、矩陣與清單，避免長篇散文。

## 設計輔助標記

結案報告必須有 `id="design-assist"` 欄位，內容依實際情況使用：

- Claude Design
- 內建模板（Claude Design 無法使用）
- 內建模板

不得宣稱使用未實際使用的設計工具。

## 驗證

- 所有 HTML 使用 UTF-8，根元素標示 `lang="zh-Hant"`、正確 `data-report-profile` 與生命週期狀態。
- Spec 文件前言中的 `工作識別碼` 與 `狀態` 都只能在指定位置及全文件各出現一次；結案與 Grill-me 驗證時，`狀態` 必須精確為「已核准」。
- Ticket 的狀態、前端七個驗收欄位、Developer／Reviewer／Finding／最終驗收欄位，以及 Brownfield 原有功能五個欄位，必須各自在指定章節恰好出現一次，且全 Ticket 也恰好出現一次。實作流程要直接替換 Ticket 內既有欄位值，禁止在文件尾端或其他章節追加第二份欄位；重複、矛盾或缺漏一律拒絕。
- 驗證器機器檢查工作識別、路徑、需求覆蓋、精確狀態、Reviewer／Finding 摘要、適用的原生瀏覽器證據及 HTML 安全邊界。實際 Diff、版本、完整測試輸出、風險與回復細節仍由 Coordinator 從來源證據負責，不能因 validator exit `0` 就省略或推定存在。
- 結案報告必須包含原始需求、Ticket 成果、實際驗收、風險與回復、使用者確認清單及設計輔助標記。
- 適用的使用者介面需求必須有原生瀏覽器實際操作證據；不適用時必須有判定依據。
- 產物不得殘留雙大括號、TODO、未替換提示或另一呼叫者的模板識別。
- 動態專案名稱、路徑、標題與純文字一律先做 HTML escape。結案模板的事實內容填入 `data-dynamic-text` 純文字槽；規劃報告若需要表格、清單等結構，只能使用驗證器允許的安全結構標籤。任何報告都不得自行加入 script、iframe、事件屬性、可執行 URL、style 區塊或 style 屬性；只有固定模板內建且內容完全一致的 checklist JavaScript 可以保留，而且該 `script` 不得有任何屬性，包含 `src`。
- 使用者確認清單只使用固定安全結構；不得加入 `hidden`、`disabled`、`checked`、`aria-hidden`、`inert`，也不得用 `display:none`、`visibility:hidden`、`pointer-events:none` 或 `opacity:0` 隱藏或停用清單。Implement 與 Brownfield Implement 的整份 `style` 必須與固定 completion 模板完全一致，所有元素與屬性也只能使用固定 completion allowlist，不能加入 `details`、額外表單控制項、未知屬性或其他包裝繞過。每個 `input[type="checkbox"]` 的 `id` 必須等於 `data-requirement-id`，該需求 ID 在全文件只能出現一次，並恰好對應一個 `label`；label 必須逐字顯示 `R-ID：Spec 原始需求原文`，不可摘要、改寫或省略。
- 每個 Spec `R-xxx` 至少要被一張 Ticket 的「對應原始需求」引用；Ticket 不得引用 Spec 不存在的 ID，也必須逐字保留該 ID 對應的原始需求。HTML 清單不能代替 Ticket 覆蓋證據。
- 新工作同時核對工作目錄名稱、Spec `工作識別碼` 與 HTML `data-work-id`。舊工作若 Spec 尚無 `R-xxx`，必須先在每張 Ticket 的「對應原始需求」建立 `R-LEGACY-001` 起的原文對照；不得退回只檢查至少一個勾選框。
