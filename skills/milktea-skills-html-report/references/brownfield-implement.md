# 既有系統重構實作：重構完成與相容性驗收報告

## 用途

重構完成後，證明「架構真的改善，而且原有功能沒有被破壞」。

這份報告不能只是一般 Implement 報告換顏色，必須特別重視清理結果、架構差異、原有功能與相容性。

## 產生時間

所有重構 Tickets、Review、修正、原有功能確認及最終總驗收完成後，只產生一次。

只有呼叫者識別為 brownfield-implement，而且所有必須保留功能都已使用 Planner 指定的相同方法完成修改後確認時才能產生。固定寫入 docs/work/功能名稱/completion-report.html。

單張 Ticket、單次 Review、修正、複驗或單項原有功能確認時都不能產生或更新 HTML。

## 首頁先回答

- 重構是否完成。
- 原有功能是否全部保留。
- 清理了多少重複或廢棄內容。
- 架構複雜度改善多少。
- 回歸測試是否全部通過。
- 是否仍有未知或保留候選。
- 如果沒有未完成項目，直接顯示「全部完成」。

## 報告主要內容

### 原始重構目標

- Planner 核准的改善方案。
- 使用者核准的重構範圍。
- 必須保留的原有功能。
- 每個重構目標的實際完成狀態與驗收證據。
- 未核准範圍不得混入成果；若實際修改超出範圍，必須列出修改內容、理由及使用者授權證據。

### 清理與修改結果

- 哪些內容保留、搬移、合併、封存、重建或移除。
- 每項處置的實際路徑。
- 每項處置解決什麼問題。
- 判斷及執行證據。
- 可能影響與回復方式。
- Planner 報告中的候選與最終實際處置逐項對照。
- 額外發現但沒有處理的項目要分開列出，說明原因與建議下一步。

### 架構與資料流前後差異

- 修改前架構。
- 修改後架構。
- 模組責任與資料所有權如何變化。
- 共用水管、依賴、共享狀態及副作用如何收斂。
- 公開介面與外部整合是否保持相容。
- 實際結果是否偏離 Planner 核准方案；有偏離就說明原因、影響及核准證據，沒有就寫「實際結果符合核准方案」。

### 改善與相容性數據

每個改善指標都要列出修改前、修改後、差值、百分比、單位、計算方式及證據來源。

優先比較：

- 模組數量與責任邊界。
- 重複程式碼或重複文件。
- 依賴、層級與入口數量。
- 共用水管與循環依賴。
- 人工操作步驟。
- 警告、測試或執行時間。

所有必須保留功能都要顯示修改前驗證、修改後驗證及通過標準。沒有可靠基準的項目直接寫「無法量化：缺少修改前基準」，不能編造數字。

### 最終安全驗收

- 回歸測試的名稱、實際指令或方法、結果及退出碼。
- Reviewer A／B 各自的最終結果。
- Findings 提出、修正、反駁、關閉或撤回的摘要。
- 原有功能確認矩陣，逐項顯示修改前證據、修改後結果及是否通過。
- 未完成事項：
  - 列出對應重構目標、未完成原因、實際影響及下一步。
  - 沒有未完成事項就明確寫「全部完成」。
- 未知區域與未解風險：
  - 說明未知或風險是什麼、可能影響什麼、觸發條件及目前如何降低風險。
  - 沒有就分別寫「沒有已知未知區域」及「沒有已知未解風險」。
- 回復方式：
  - 說明什麼情況需要回復、要還原哪些程式或資料、實際步驟及回復後如何重新驗證原有功能。
- 人工下一步：
  - 說明由誰、在什麼情況、執行什麼操作，以及預期結果。
  - 沒有人工下一步就寫「不需要人工處理」。

## 視覺風格

- 定位是「系統翻修成果與安全稽核報告」。
- 主色使用深青、森林綠及橘色風險提示。
- 核心畫面是架構前後對比及原有功能保留。
- 清理結果使用「保留／合併／封存／移除／重建」分類視覺。
- 整體比一般 Implement 更嚴謹，強調可回復、相容性與證據。
- 不能只用漂亮的完成率掩蓋未知風險。

## 聊天框

只顯示「重構與相容性驗收通過」及 HTML 報告連結，不逐票重述執行與 Review 資料。
