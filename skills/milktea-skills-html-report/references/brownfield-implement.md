# 既有系統重構結案報告契約

## 用途與產生時間

證明本次核准重構已完成，而且 Planner 指定的原有功能與相容性沒有被破壞。只有呼叫者識別為 `brownfield-implement`，所有 Tickets、Review、修正、定向複驗、原有功能確認與最終總驗收均完成時才能產生。

先寫入 `<實際工作目錄>/completion-report.pending.html`。使用 `--candidate --publish` 嚴格驗證並原子發布後，使用者才會得到 `<實際工作目錄>/completion-report.html`；正式檔已存在時必須停止，不得覆寫。

## 必要輸入

- 工作識別碼、繁體中文顯示名稱與實際工作目錄。
- Planner HTML、核准方案、Spec、全部 Tickets、實際差異與版本。
- 必須保留功能、修改前基準、修改後相同方法驗證及相容性結果。
- 測試、Reviewer、Finding、修正、定向複驗、清理處置及未解風險。
- 每張 Ticket 的前端實際操作適用性、判定依據與實際證據。
- Spec「原始需求」內每項 `R-xxx`，以及每張 Ticket 的精確 Developer、Reviewer、Finding、Ticket 最終驗收與原有功能證據。

## 需求與相容性驅動內容

報告使用彈性 HTML 外殼，不強迫固定專案章節。至少回答：

1. 最終結論：核准重構與相容性是否全部通過。
2. 原始重構目標：逐項顯示核准目標、範圍、實際結果與證據。
3. Ticket 成果：白話說明每張 Ticket 的處置、Review 結論、清理結果及是否偏離核准方案。
4. 實際驗收：回歸測試、退出碼、原生瀏覽器操作或不適用依據、Findings 關閉情況，以及每項必須保留功能的修改前後證據。
5. 風險與回復：未知區域、未解風險、觸發條件、降低方式、回復步驟及回復後相容性驗證。
6. 使用者確認：checkbox 只依 Spec 原始需求的 `R-ID` 逐項建立；必須保留功能留在原有功能驗收矩陣，不另設 checkbox。這是使用者清點工具，不取代 Agent 已完成的技術驗收。

只有真實資料足夠時才增加架構差異、清理統計、改善數據或圖表。缺少可靠基準時使用「無法量化：缺少修改前基準」，不得製造數字。

## 精確驗證欄位

- 沿用 Implement 契約的 `Developer 結論`、`Reviewer 模式`、Reviewer A／B 結論、`未關閉阻擋或重要 Findings`、`Ticket 最終驗收`、前端七個驗收欄位與需求清單規則。
- 每張 Ticket 的「原有功能確認」必須各自且只填一次 `共用驗證方法`、`修改前基準`、`修改後結果`、`原有功能驗收`、`驗收證據`；這五個欄位在全 Ticket 也只能各出現一次。`原有功能驗收` 必須精確為「通過」，其餘四項必須是非空、非占位且可確認的實際內容。
- `驗收證據` 不得使用「無法確認、假設、推測、不確定、未驗證」等不可靠文字。實作流程必須原地替換 Ticket 已有的五個欄位，不能在別處追加另一組。
- UI／使用者可操作功能使用 Claude／Codex 原生瀏覽器驗收；API、CLI、Worker、Migration 等非 UI 功能標記前端「不適用」並提供判定依據，再使用對應 API、CLI、測試或修改前後同方法證據驗收。
- 所有動態文字先 HTML escape；只使用固定模板及安全 checkbox 結構。

## 狀態用語

核准目標狀態只使用「完成、部分完成、未完成、範圍外」。本報告只有全部核准目標及必須保留功能均完成且驗收通過時才能產生。

## 聊天框

只顯示「重構與相容性驗收通過」及結案報告絕對路徑連結，不逐票重述證據。
