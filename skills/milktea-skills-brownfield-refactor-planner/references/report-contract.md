# Brownfield HTML 報告契約

產生 HTML 前完整讀取本文件。報告的用途是讓使用者快速驗證 Planner 是否真正理解專案、決定清理邊界，並把核准內容交給下一個 Implement Task。

## 儲存與版本

- 固定寫入 `docs/architecture-reviews/YYYY-MM-DD-<範圍>.html`。
- `<範圍>` 使用簡短 kebab-case；同日同名才追加 `-02`、`-03`。
- 更新同一次規劃時覆寫同一份報告，不建立 `final`、`new`、`v2` 副本。
- 報告只引用本專案可讀取的 Spec、Tickets、規劃文件與 ADR；不得依賴 Skill 安裝目錄。
- 不為報告執行 Commit、Push、部署或建立伺服器。

## 資訊設計

使用最少文字傳遞最多可判定資訊：

1. 首屏放結論、範圍、最大風險、推薦方案與待核准事項。
2. 一個概念只說一次；細節以連結、表格或 `<details>` 展開。
3. 每段先寫結論，再放證據；避免連續長段落。
4. 比較、映射、依賴與狀態優先使用表格或圖，不用散文重複描述。
5. 目錄、模組、遷移與執行順序優先使用文字樹或 Mermaid。
6. 原始命令輸出只保留判斷所需片段，完整內容放可展開區塊。
7. 明確區分「已確認」「推論」「候選」「未知」「未驗證」。

## 必備內容與最佳視覺形式

| 內容 | 優先形式 |
|---|---|
| 專案用途與使用者流程 | 一段摘要＋流程圖 |
| 掃描範圍、Git 狀態與未知區域 | Snapshot 卡片＋範圍表 |
| Code／Data／Runtime Root | Root／真實路徑／所有權表 |
| 完整但精簡的目錄 | 文字目錄樹 |
| 現況架構 | Mermaid 架構圖 |
| 模組責任與資料所有權 | 責任矩陣 |
| 端到端資料流 | Mermaid 流程圖 |
| 正式 Log 判定 | 不需要：一句結論；需要：錯誤流圖＋Logger 契約表 |
| 共用 Hook／API／component 使用位置 | 呼叫位置表或關係圖 |
| 危險共用水管 | 風險熱點表 |
| 架構規範差異 | 現況／規範／處置比較表 |
| 命名、重複與過度分層 | 候選與證據表 |
| 垃圾、廢棄功能與舊資料候選 | 清理候選表 |
| 保留、刪除、封存、合併、重建建議 | 決策矩陣 |
| 局部整理與重建比較 | 方案比較表 |
| 建議目標目錄 | 文字目錄樹 |
| 目標架構與遷移 | Mermaid 遷移圖 |
| Spec 摘要 | 目標／範圍／驗收卡片 |
| Tickets、依賴與執行順序 | Mermaid 依賴圖＋Ticket 表 |
| 測試、回歸、回滾與風險 | 驗證矩陣＋風險表 |
| Agent 不確定或需確認事項 | 核准清單 |

## 必備章節

### 1. 決策摘要

- 用一句話說明專案做什麼。
- 列出本次建議處理範圍及明確不處理範圍。
- 顯示推薦方案、最大三項風險與使用者必須決定的事項。

### 2. 現況 Snapshot

至少顯示：

- 專案根目錄、Git SHA、工作樹狀態、OS／Shell。
- 掃描時間、掃描範圍、排除範圍及未知區域。
- Code／Data／Runtime Root 的設定路徑、解析後路徑、是否進 Git 與資料所有者。
- 已執行的基準命令、結果、版本與未執行理由。

Git SHA 只用來標示報告分析的已提交版本，不會鎖定檔案。工作樹有未提交修改時，必須同時顯示狀態及必要的 Diff 摘要；不得要求使用者先 Commit，也不得建立 SHA／Hash Manifest、Checksum Guard、CI／Git Hook 驗證或其他修改阻擋機制。

工作樹原有修改必須獨立標示，不能列為垃圾候選或當成本次輸出。

### 3. 現況架構與資料流

- 顯示精簡目錄樹、入口、主要模組、資料儲存、外部整合及測試接縫。
- 顯示模組責任、資料所有權和公開契約。
- 畫出使用者動作到資料或外部服務的端到端資料流。
- 先顯示專案是否已有正式 Log，以及是否包含背景 Worker／排程、長時間無人看守的程式，或 Web API／多人使用系統。
- 沒有正式 Log 且不符合上述任一情況時，只寫「正式 Log：不需要」及判斷依據，不建立錯誤流圖或 Logger 契約表。
- 已有正式 Log 或符合任一情況時，才畫出錯誤從發生位置到使用者訊息與正式 Log 的流向，並列出 Logger 位置、輸出目的地、格式、必要欄位、error code、追蹤 ID、輪替、保存、機密遮蔽與實際使用範例。
- Console 輸出及 `milktea-skills-debug` 的臨時 Debug Log 不列為正式 Log。需要正式 Log 但專案尚未建立時，優先建議使用專案語言或框架原生 Logging；只有確實需要統一格式、錯誤碼或多個輸出目的地時才包裝 Logger。
- 在圖中標出共享狀態、副作用、循環依賴與高風險水管。

### 4. 共用使用位置

對每個可能受重構影響的共用 Hook、API、component、service、repository、Schema、CLI 或事件列出：

- 定義位置與公開介面。
- 所有已確認的直接及間接使用位置。
- 是否被原始問題範圍以外的頁面或流程使用。
- 動態或設定驅動引用的查證方式。
- 修改影響與建議的安全接縫。

### 5. 精簡與垃圾候選

每項候選至少包含：

| 欄位 | 說明 |
|---|---|
| 項目 | 路徑、符號、資料集或功能 |
| 類型 | 重複／過度分層／廢棄／測試殘留／生成物／舊資料／未知 |
| 證據 | 引用、產生者、讀寫者、Git 或執行證據 |
| 建議 | 保留／刪除／封存／合併／重建／待查 |
| 風險 | 可能破壞的功能或資料 |
| 回復 | 可重建來源、備份或回滾方法 |
| 核准 | 是否需要使用者明確決定 |

沒有引用的檔案只能標為候選。無法排除動態使用、外部使用或正式資料時，標為未知。

### 6. 方案與目標架構

- 至少比較「局部整理」與「局部或整段重建」；確實沒有重建價值時說明證據，不硬湊方案。
- 比較變更量、可讀性、刪減效果、相容風險、資料遷移、測試成本、回滾與長期維護。
- 顯示推薦目標目錄樹、模組責任、資料所有權與公開介面。
- 清楚標示保留、搬移、合併、新建與移除的節點。

### 7. Spec、Tickets 與遷移順序

- 摘要 Spec 的問題、目標、範圍、相容要求及驗收條件。
- 列出每張 Ticket 的目標、依賴、修改邊界、驗證與回復點。
- 以圖表示順序、阻擋關係與可安全平行工作。
- 不把相依工作偽裝成可平行，也不建立無法獨立驗證的純分層 Ticket。

### 8. 原有功能確認

對所有標示為必須保留的行為建立矩陣：

| 保留行為 | 修改前證據 | 修改後相同驗證 | 通過標準 | 覆蓋限制 |
|---|---|---|---|---|

證據可包含測試、Build、Typecheck、Lint、API／Schema 比較、CLI 輸出、資料不變量、關鍵使用者流程及必要的人工驗證。任何必須保留的功能無法建立或重跑驗證時，列為完成阻擋並交由使用者處理。

### 9. 核准事項

只列真正需要使用者判斷的選項：

- 刪除、封存、合併或重建邊界。
- 無法自動驗證但必須保留的行為。
- 資料遷移、停機、相容或回滾取捨。
- 推薦方案與替代方案的主要代價。

## HTML 實作要求

- 使用語意化 HTML、清楚標題階層、鍵盤可操作元素、可辨識焦點及足夠色彩對比。
- 支援桌面與窄螢幕，並提供可列印樣式。
- 可使用 Tailwind CSS CDN 與 Mermaid CDN，不建立前端專案或新增套件。
- Mermaid 設為 `securityLevel: 'strict'`；圖表失敗時仍須保留可讀文字或表格，不能讓資訊消失。
- 不需要後端、資料庫、追蹤碼或部署流程。
- 不嵌入機密、Token、Cookie、完整環境變數或不必要的個人資料。
- 外部連結與本機檔案路徑使用明確標籤；不要用「點這裡」。

## 驗收

- 首屏即可理解專案用途、推薦方案、風險與待核准事項。
- 所有重要圖表都能由旁邊的表格或文字驗證，不以裝飾取代資訊。
- 所有刪除或重建建議都有實際證據、風險與回復方式。
- Spec、Tickets、HTML 和來源證據互相一致，沒有第二套決策。
- 報告明確區分已證明的相容範圍與未驗證區域，不宣稱絕對零風險。
