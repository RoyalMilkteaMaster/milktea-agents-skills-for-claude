> **可選項：一般中小型專案使用milktea開發不需要Logging 系統。**

# 中型專案Logging 架構：從零建立標準

本文件只供確實需要長期保存執行紀錄的新專案使用。

## 目的

需要正式 Log 的專案，從第一天固定寫入入口、格式和存放位置，避免不同功能各自建立 Log。

本文件只規定從零建立的新專案。既有專案如何整理，由相關 Skill 處理。

## 存放位置

程式碼與執行資料分開存放：

```text
工作目錄/
├─ shop-system/          # 程式碼專案
└─ shop-system_data/     # 程式執行後產生的資料
   └─ logs/              # 所有正式 Log 的固定位置
```

所有正式 Log 統一放在：

```text
<專案名稱>_data/logs/
```

程式碼專案內不建立正式 `logs/`，不同功能也不能自行建立其他 Log 位置。外部資料資料夾的實際路徑，由專案原本的設定機制提供。

## 資料流程

```text
各項功能
  → 共用 Logger
  → 補齊欄位並移除敏感資料
  → 寫入 <專案名稱>_data/logs/
```

登入、訂單、排程等功能需要留下紀錄時，都呼叫同一個共用 Logger。各功能只提供要記錄的內容，不自行建立檔案、決定路徑或定義另一套格式。

底層優先使用語言或框架現有的 Logging 功能。共用 Logger 只負責統一欄位、過濾敏感資料和控制輸出位置，不另外重做完整系統。

## 檔案安排

單一程式預設使用：

```text
logs/
├─ app.jsonl
├─ app-2026-08-01.jsonl
└─ app-2026-08-02.jsonl
```

- `app.jsonl`：目前正在寫入的 Log。
- 含日期的檔案：輪替後保留的舊 Log。

多個獨立執行的程式使用不同檔名：

```text
logs/
├─ api.jsonl
├─ worker.jsonl
└─ scheduler.jsonl
```

不要讓多個程式同時寫入同一個檔案，也不要依照登入、訂單或商品等功能拆成不同資料夾。功能來源記錄在 Log 欄位中。

## 格式與欄位

正式 Log 使用 JSONL，每一行代表一筆完整紀錄：

```json
{"timestamp":"2026-08-03T10:15:20+08:00","level":"ERROR","event":"order_create_failed","source":"order","message":"建立訂單失敗","errorCode":"ORDER_CREATE_FAILED"}
```

每筆 Log 必須包含：

- `timestamp`：發生時間。
- `level`：`INFO`、`WARNING` 或 `ERROR`。
- `event`：固定且可搜尋的事件名稱。
- `source`：產生紀錄的功能或程式。
- `message`：簡短說明。

需要時才加入 `errorCode`、`traceId` 或其他查錯資料。

## 記錄原則

只記錄程式結束後仍需要追查的內容：

- 背景工作、排程或重要流程的完成與失敗。
- 程式崩潰和未預期錯誤。
- 外部 API、資料庫或其他依賴的失敗。
- 需要跨步驟追查的重要操作結果。

不得記錄密碼、Token、API Key、完整付款資料、不必要的個人資料或整包未清理的 Request／Response。

同一個錯誤只在最能說明原因和結果的位置記錄一次。函式進出、變數內容及為了驗證假設加入的訊息屬於臨時 Debug Log，不進入正式 Log。

## 輪替與清理

Log 達到指定大小或日期改變時，將目前檔案改名保存，並在同一個 `logs/` 裡建立新的目前檔案。輪替不改變 Log 的存放位置。

每個專案自行決定：

- 預估每日 Log 容量。
- 檔案何時輪替。
- Log 可以使用的磁碟空間。
- 舊 Log 的保存期限。
- 超過期限後的清理方式。

正在寫入、正在調查或有保存要求的 Log，不得自動刪除。

## 適用範圍

此架構適用於有以下需求，且主要在本機或單一環境執行的中型專案。

- 背景 Worker 或排程。
- 長時間無人看守的程式。
- Web API 或多人使用系統。

跨平台或多台電腦的大型專案，應改使用 Collector 將 Log 傳到集中式後台。
