# Brownfield 架構健檢 HTML 報告契約

產生 HTML 前完整讀取本文件。報告的用途是讓使用者在產生 Spec 與 Tickets 以前，先確認 Agent 是否真正理解專案，並決定是否值得繼續重構規劃。

## 儲存與版本

- 固定寫入 `docs/architecture-reviews/YYYY-MM-DD-<範圍>.html`。
- `<範圍>` 使用簡短 kebab-case；同日同名才追加 `-02`、`-03`。
- 同一次盤點更新同一份報告，不建立 `final`、`new` 或 `v2` 副本。
- 報告只引用本專案可讀取的規劃文件、ADR 與來源證據；不得依賴 Skill 安裝目錄。
- 報告產生時不要求 Spec 或 Tickets 已存在，也不建立或更新它們。
- 不為報告執行 Commit、Push、部署或建立伺服器。

## 資訊設計

1. 首屏放結論、範圍、最大風險、推薦方案與待決策事項。
2. 一個概念只說一次；細節以連結、表格或 `<details>` 展開。
3. 每段先寫結論，再放證據；避免連續長段落。
4. 比較、映射、依賴與狀態優先使用表格或圖。
5. 目錄、模組、資料流與遷移優先使用文字樹或 Mermaid。
6. 原始命令輸出只保留判斷所需片段，完整內容放可展開區塊。
7. 明確區分「已確認」「推論」「候選」「未知」「未驗證」。

## 必備內容與最佳視覺形式

| 內容 | 優先形式 |
|---|---|
| 專案用途與使用者流程 | 一段摘要＋流程圖 |
| 掃描範圍、Git 狀態與未知區域 | Snapshot 卡片＋範圍表 |
| Code／Data／Runtime Root | Root／真實路徑／所有權表 |
| 精簡目錄 | 文字目錄樹 |
| 現況架構 | Mermaid 架構圖 |
| 模組責任與資料所有權 | 責任矩陣 |
| 端到端資料流 | Mermaid 流程圖 |
| 正式 Log 判定 | 不需要：一句結論；需要：錯誤流圖＋Logger 契約表 |
| 共用 Hook／API／component 使用位置 | 呼叫位置表或關係圖 |
| 危險共用水管 | 風險熱點表 |
| 架構規範差異 | 現況／規範／處置比較表 |
| 重複、過度分層與廢棄候選 | 候選與證據表 |
| 保留、刪除、封存、合併、重建建議 | 決策矩陣 |
| 局部整理與重建比較 | 方案比較表 |
| 候選目標目錄 | 文字目錄樹 |
| 候選目標架構與遷移 | Mermaid 遷移圖 |
| 必須保留的功能與現有驗證 | 驗證矩陣 |
| 風險、回滾與未知 | 風險表＋待決策清單 |

## 必備章節

### 1. 決策摘要

- 用一句話說明專案做什麼。
- 列出本次掃描範圍及明確不處理範圍。
- 顯示是否值得重構、推薦方案、最大三項風險與待決策事項。
- 明確提示：使用者可只保留本報告，尚未產生 Spec 或 Tickets。

### 2. 現況 Snapshot

- 專案根目錄、Git SHA、工作樹狀態、OS／Shell。
- 掃描時間、掃描範圍、排除範圍及未知區域。
- Code／Data／Runtime Root 的設定路徑、解析後路徑、是否進 Git 與資料所有者。
- 已執行的基準命令、結果、版本與未執行理由。

Git SHA 只標示已提交版本。工作樹有未提交修改時，同時顯示狀態及必要 Diff 摘要；不得要求使用者先 Commit，也不得建立會阻擋修改的 Hash／Checksum 機制。

### 3. 現況架構與資料流

- 顯示精簡目錄樹、入口、主要模組、資料儲存、外部整合及測試接縫。
- 顯示模組責任、資料所有權和公開契約。
- 畫出使用者動作到資料或外部服務的端到端資料流。
- 標出共享狀態、副作用、循環依賴與高風險水管。
- 列出動態或設定驅動引用的查證方式及未知區域。

### 4. 正式 Logging 判定

- 先顯示專案是否已有正式 Log，以及是否包含背景 Worker／排程、長時間無人看守的程式，或 Web API／多人使用系統。
- 沒有正式 Log 且不符合任一情況時，只寫「正式 Log：不需要」及判斷依據。
- 已有正式 Log 或符合任一情況時，才顯示錯誤流向及 Logger 位置、目的地、格式、必要欄位、error code、追蹤 ID、輪替、保存與機密遮蔽。
- Console 輸出及 `milktea-skills-debug` 的臨時 Debug Log 不列為正式 Log。

### 5. 共用使用位置

對可能受重構影響的共用 Hook、API、component、service、repository、Schema、CLI 或事件列出：

- 定義位置與公開介面。
- 已確認的直接及間接使用位置。
- 是否被原始範圍以外的頁面或流程使用。
- 修改影響與建議的安全接縫。

### 6. 精簡與清理候選

每項候選至少包含：

| 欄位 | 說明 |
|---|---|
| 項目 | 路徑、符號、資料集或功能 |
| 類型 | 重複／過度分層／廢棄／測試殘留／生成物／舊資料／未知 |
| 證據 | 引用、產生者、讀寫者、Git 或執行證據 |
| 建議 | 保留／刪除候選／封存候選／合併候選／重建候選／未知 |
| 風險 | 可能破壞的功能或資料 |
| 回復 | 可重建來源、備份或回滾方法 |

沒有引用的檔案只能標為候選。無法排除動態使用、外部使用或正式資料時，標為未知。

### 7. 改善方案與候選目標架構

- 比較局部整理與局部或整段重建；沒有重建價值時說明證據。
- 比較變更量、可讀性、刪減效果、相容風險、資料遷移、驗證成本、回滾與長期維護。
- 顯示候選目標目錄、模組責任、資料所有權、公開介面與遷移順序。
- 清楚標示保留、搬移、合併、新建與移除候選。
- 推薦一個方案，並說明主要代價及何時不該做。

### 8. 原有功能與驗證基準

對必須保留的行為建立初步矩陣：

| 保留行為 | 目前證據 | 重構後應重跑的相同驗證 | 通過標準 | 未知或限制 |
|---|---|---|---|---|

這是後續 Spec 與 Tickets 的輸入，不代表重構已被核准。無法建立驗證方式時，列為未知或阻擋。

### 9. 待決策事項

只列真正需要使用者判斷的選項：

- 是否只保留報告，或繼續產生重構 Spec 與 Tickets。
- 要採用、拒絕或延後的改善候選。
- 刪除、封存、合併或重建邊界。
- 無法自動驗證但必須保留的行為。
- 資料遷移、相容與回滾取捨。

## HTML 實作要求

- 使用語意化 HTML、清楚標題階層、鍵盤可操作元素、可辨識焦點及足夠色彩對比。
- 支援桌面與窄螢幕，並提供可列印樣式。
- 可使用 Tailwind CSS CDN 與 Mermaid CDN，不建立前端專案或新增套件。
- Mermaid 設為 `securityLevel: 'strict'`；圖表失敗時仍須保留可讀文字或表格。
- 不需要後端、資料庫、追蹤碼或部署流程。
- 不嵌入機密、Token、Cookie、完整環境變數或不必要的個人資料。
- 外部連結與本機檔案路徑使用明確標籤；不要用「點這裡」。

## 驗收

- 首屏即可理解專案用途、是否值得重構、推薦方案、風險與待決策事項。
- 所有重要圖表都能由旁邊的表格或文字驗證。
- 所有刪除或重建候選都有實際證據、風險與回復方式。
- 報告能獨立交付，不依賴尚未產生的 Spec 或 Tickets。
- 報告明確區分已證明的相容範圍與未知區域，不宣稱絕對零風險。
- 報告沒有替使用者決定是否進入 Spec、Tickets 或實作階段。
