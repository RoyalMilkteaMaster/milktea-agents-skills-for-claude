# Brownfield 架構健檢 HTML 報告契約

報告用來幫助使用者快速看懂現況、問題與改善選項，再決定是否繼續規劃。使用繁體中文與白話短句；除實際技術名稱、程式符號、路徑及命令外，盡量不使用英文。

## 儲存方式

- 固定寫入 `docs/architecture-reviews/YYYY-MM-DD-<範圍>.html`。
- `<範圍>` 使用簡短 kebab-case；同日同名才追加 `-02`、`-03`。
- 同一次盤點更新同一份報告，不建立 `final`、`new` 或 `v2` 副本。
- 報告不要求 Spec 或 Tickets 已存在，也不建立或更新它們。
- 不為報告執行 Commit、Push、部署或建立伺服器。
- 報告頂部提供簡短且可點擊的章節目錄。

## 表達原則

1. 先顯示結論，再補證據；一個概念只說一次。
2. 可以用表格講清楚的資料，不改寫成多段文字。
3. 現況目錄固定使用精簡文字樹；結構會改變時，再顯示一份目標文字樹。
4. 每個重要目錄或檔案右側都用繁體中文短句備註用途。
5. 架構、資料流、依賴與遷移順序優先使用 Mermaid 圖。
6. 圖表旁保留簡短文字或表格，確保圖表載入失敗時仍看得懂。
7. 明確區分「已確認」「推論」「候選」「未知」與「未驗證」。
8. 原始命令、Diff 或較長證據放入 `<details>`，正文只保留判斷需要的片段。
9. 只保留會影響理解或重構決策的內容。

不要為了視覺化硬畫圖。只有一兩個項目或一句話就能說清楚時，直接寫短句。

文字樹使用以下形式：

```text
src/
├─ api/                 # 接收前端與外部請求
├─ services/            # 放置主要業務流程
├─ repositories/        # 負責資料讀寫
└─ shared/              # 多個模組共同使用的程式
```

不要展開依賴快取、建置輸出或大量重複葉節點。備註說明「這裡負責什麼」，不重複檔名。

## 報告內容

### 1. 決策摘要

首屏直接顯示：

- 專案用途與本次掃描範圍。
- 是否值得重構及推薦方向。
- 最大三項風險。
- 需要使用者決定的事項。
- 使用者可以只保留報告，不繼續產生 Spec 或 Tickets。

使用摘要卡片或短表格呈現，不寫長篇前言。

### 2. 現況架構與資料流

先用一張精簡 Snapshot 表格顯示專案根目錄、Git SHA、工作樹狀態、掃描範圍、排除範圍、程式碼／資料／執行根目錄，以及已執行的基準驗證。

接著固定顯示：

- 一份附右側繁體中文用途備註的現況文字樹。
- 一張現況架構圖，顯示主要入口、模組、資料儲存、外部整合及測試接縫。
- 一張端到端資料流圖，顯示資料由誰產生、誰修改、流向哪裡；流程很簡單時可與架構圖合併。
- 一張責任表，列出模組責任、資料所有權與公開介面。
- 一張根目錄表，列出程式碼、資料與執行環境的設定路徑、實際路徑及所有者。

專案有明確使用者操作流程時，以流程圖顯示使用者動作如何進入系統並產生結果。共用狀態、循環依賴、隱性副作用或動態引用只有影響判斷時才補充。每個重要結論附實際路徑、符號、命令或測試證據。

### 3. 問題與清理候選

使用同一張表格列出重複、過度分層、廢棄內容、錯放資料、危險共用位置與其他問題：

| 項目 | 類型 | 現況與證據 | 建議 | 可能影響 | 回復方式 |
|---|---|---|---|---|---|

建議只能標示為保留、刪除候選、封存候選、合併候選、重建候選或未知。搜尋不到使用位置不能直接判定可刪除。

候選會影響共用 Hook、API、元件、服務、資料存取、Schema、CLI 或事件時，再加入一張簡短使用位置表，列出定義位置、主要呼叫者、範圍外使用位置與可能影響；沒有受影響的共用位置時不建立空表。

正式 Logging 只有在專案已有正式 Log，或包含背景 Worker、排程、長時間無人看守程式、Web API 或多人使用系統時才檢查；不需要時只寫一句結論。

### 4. 改善方案

使用一張比較表呈現真正有差異的方案：

| 方案 | 主要改動 | 優點 | 代價與風險 | 驗證與回滾 | 建議 |
|---|---|---|---|---|---|

只提出有必要的方案，不硬湊數量。需要顯示目標架構或遷移順序時，使用一張 Mermaid 圖；沒有重建價值時直接說明，不建立重建方案。

推薦方案會改變目錄或模組責任時，必須顯示一份附右側繁體中文用途備註的目標文字樹，並在名稱旁標示保留、搬移、合併、新建或移除候選。架構或資料流會改變時，再用一張圖顯示目標狀態與遷移方向。

### 5. 保留功能、驗證與待決策事項

使用表格列出：

| 必須保留的行為 | 修改前證據 | 修改後重跑方式 | 通過標準 | 未知或限制 |
|---|---|---|---|---|

最後用短清單整理：

- 尚未確認的事實與阻擋。
- 資料遷移、相容及回滾風險。
- 使用者需要採用、拒絕或延後的候選。
- 是否只保留報告，或繼續產生重構 Spec 與 Tickets。

## HTML 要求

- 使用語意化 HTML、清楚標題層級、鍵盤可操作元素、可辨識焦點及足夠色彩對比。
- 提供簡短可點擊目錄，讓使用者直接跳到五個核心章節。
- 支援桌面、窄螢幕與列印。
- 可使用 Tailwind CSS CDN 與 Mermaid CDN，不建立前端專案或新增套件。
- Mermaid 使用 `securityLevel: 'strict'`；圖表失敗時仍保留可讀文字或表格。
- 不需要後端、資料庫、追蹤碼或部署流程。
- 不嵌入機密、Token、Cookie、完整環境變數或不必要的個人資料。
- 外部連結與本機路徑使用明確名稱，不使用「點這裡」。

## 完成條件

- 首屏可立即理解本次範圍、推薦方向、主要風險與待決策事項。
- 現況文字樹固定存在，重要目錄與檔案右側都有繁體中文用途備註。
- 結構會改變時有附用途備註的目標文字樹；結構不變時不硬湊。
- 架構與資料流優先用圖呈現；比較、責任、問題與驗證優先用表格呈現。
- 文字簡短、白話、使用繁體中文，沒有重複解釋。
- 所有重要結論都能追溯到程式、Git、測試、命令或專案文件。
- 所有刪除或重建候選都有證據、風險與回復方式。
- 報告能獨立閱讀，不依賴尚未產生的 Spec 或 Tickets。
- 報告不替使用者決定是否進入 Spec、Tickets 或實作階段。
