# Milktea Skills Grill Check Needs

確認「為什麼做、誰需要、要做到什麼」。不討論如何實作。

Spec 與 Tickets 固定留在本機 `docs/work/`。本 Skill 不詢問或記錄儲存位置。

由 Grill-me 的精簡規劃呼叫時，只確認本次成果、必須保持不變的行為與驗收結果；不建立完整需求決策樹，其餘流程不變。

## 流程

1. 讀取目前對話、專案指令、`CONTEXT.md`、既有 `docs/planning/requirements.md` 與產品行為。
2. 重述目標、已知事實與未決需求。
3. 建立需求決策樹，先問會改變其他分支的問題。
4. 一次只問一個決策，附推薦選項、理由與主要代價。
5. 確認所有需求面向後，輸出摘要並請使用者核准。
6. 使用者核准後，把完整需求寫入 `docs/planning/requirements.md`；只把已確認的專有名詞、關係與歧義更新至專案根目錄 `CONTEXT.md`。

## 文件責任

寫入時才建立必要目錄，不預建空架構。既有文件只更新本次核准範圍，保留未受影響內容。不得把完整需求、架構或可行性內容寫進 `CONTEXT.md`。

`CONTEXT.md` 固定使用：

```markdown
# Project Context

## 專有名詞

| 名詞 | 共同定義 | 備註 |
|---|---|---|

## 關係

## 歧義
```

只記錄已與使用者確認的內容。歧義未解時標示狀態，不猜測。

`docs/planning/requirements.md` 固定使用：

```markdown
# 核准需求

## 問題與使用者
## 目標結果
## 核心流程
## 必要需求
## 邊界與錯誤
## 產品限制
## 實作偏好或硬性限制
## 驗收結果
## 範圍外
## 未決事項
```

## 需求面向

- 問題、目標與成功結果。
- 使用者、觸發條件與主要流程。
- 必要功能、次要功能與範圍外項目。
- 業務規則、狀態、權限、錯誤與邊界情況。
- 平台、整合、隱私、效能、相容性等產品限制。
- 可接受的成本、時間與資源上限。
- 可由外部行為判定的驗收結果。

使用者提出執行方法時，記為「實作偏好」或「硬性限制」，不得假設它可行；交給架構階段驗證。使用者另行呼叫可行性評估時，才產生獨立報告。

## 解釋規則

- 使用者提問或表示不理解時，暫停訪談並先回答。
- 首次出現縮寫或專有名詞時，先寫全名與白話定義。
- 多個名詞依相依順序一次解釋，可提供多個選項並允許複選。
- 使用者完全不懂時，從零重講，不先反問；提供「採用 Agent 推薦方案」，說明思路後詢問是否認同。
- 能從環境確認的事實自己查，不把查詢工作丟給使用者。

## 摘要格式

```markdown
## 需求確認摘要

- 問題：
- 使用者：
- 目標結果：
- 核心流程：
- 必要需求：
- 邊界與錯誤：
- 產品限制：
- 實作偏好或硬性限制：
- 驗收結果：
- 範圍外：
- 未決事項：無／條列
```

## 完成條件

- 所有已知需求分支皆已確認或明確延後。
- 驗收結果可觀察、可判定。
- 實作方法未被誤當成已驗證事實。
- 使用者核准需求摘要。
- 核准內容已寫入 `docs/planning/requirements.md`。
- `CONTEXT.md` 只包含已確認的專有名詞、關係與歧義。
