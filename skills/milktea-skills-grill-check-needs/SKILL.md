# Milktea Skills Grill Check Needs

確認「為什麼做、誰需要、要做到什麼」。不討論如何實作。

## 流程

1. 讀取目前對話、專案指令、`CONTEXT.md` 與既有產品行為。
2. 重述目標、已知事實與未決需求。
3. 建立需求決策樹，先問會改變其他分支的問題。
4. 一次只問一個決策，附推薦選項、理由與主要代價。
5. 確認所有需求面向後，輸出摘要並請使用者核准。
6. 把已確認且會重複使用的內容寫入專案根目錄 `CONTEXT.md`。

## CONTEXT.md

首次需要寫入時才建立，不得預建其他空目錄。固定使用下列章節；未知內容寫「未確認」，不得猜測：

```markdown
# Project Context

## 產品與使用者
## 術語
## Code／Data／Runtime Roots
## 架構與資料流
## 模組責任
## 公開介面與 Schema
## 測試接縫
## 技術限制
## Issue Tracker

- 類型：
- Project／Repository：
- Spec 標籤：
- Ticket 標籤：`ready-for-agent`
- Blocking links：原生／Ticket 文字
- 必要權限：建立 Issue、留言、更新狀態

## 文件索引
## 文件與報告位置

- CONTEXT：`CONTEXT.md`
- ADR：`docs/adr/`
- 可行性報告：`docs/feasibility/`
- 架構健檢：`docs/architecture-reviews/`
- 文件資產：`docs/assets/`
- Spec：已設定的 issue tracker
- Tickets：已設定的 issue tracker
- 執行、Debug、Git 衝突與 Review 證據：對應 Ticket comments
```

專案已有自訂路徑時保留並記錄實際位置，不建立第二套來源。

## 需求面向

- 問題、目標與成功結果。
- 使用者、觸發條件與主要流程。
- 必要功能、次要功能與範圍外項目。
- 業務規則、狀態、權限、錯誤與邊界情況。
- 平台、整合、隱私、效能、相容性等產品限制。
- 可接受的成本、時間與資源上限。
- 可由外部行為判定的驗收結果。

使用者提出執行方法時，記為「實作偏好」或「硬性限制」，不得假設它可行；交給架構與可行性階段驗證。

## 解釋規則

- 使用者提問或表示不理解時，暫停訪談並先回答。
- 首次出現縮寫或專有名詞時，先寫全名與白話定義。
- 多個名詞依相依順序一次解釋，可提供多個選項並允許複選。
- 使用者完全不懂時，從零重講，不先反問；提供「採用 Agent 推薦方案」，說明思路後詢問是否認同。
- 能從環境確認的事實自己查，不把查詢工作丟給使用者。

## 摘要格式

```markdown
## 需求確認摘要

- 問題：
- 使用者：
- 目標結果：
- 核心流程：
- 必要需求：
- 邊界與錯誤：
- 產品限制：
- 實作偏好或硬性限制：
- 驗收結果：
- 範圍外：
- 未決事項：無／條列
```

## 完成條件

- 所有已知需求分支皆已確認或明確延後。
- 驗收結果可觀察、可判定。
- 實作方法未被誤當成已驗證事實。
- 使用者核准需求摘要。
