# Milktea 規格整理

把已核准內容整理成唯一規格來源。全程使用繁體中文；程式識別字保留原文。

## 前提

下列內容必須已核准：

- `docs/planning/requirements.md` 的需求與驗收結果。
- `docs/planning/architecture.md` 的架構、資料流與測試接縫。

需求或架構缺少或互相衝突時停止，指出應回到哪個階段；不得自行補問或猜測。

## 儲存位置

- 新工作固定使用本機 Markdown：`docs/work/<工作識別碼>/spec.md`。
- 上游已提供工作識別碼時原樣沿用，不得重新產生。沒有上游時，在第一次寫入前產生 `wp-YYYYMMDD-HHmmss-xxxxxxxx`；尾碼使用八位小寫十六進位字元，若目錄已存在就重新產生，不能覆寫。
- 工作識別碼只負責唯一性。另保存繁體中文顯示名稱：使用者有提供總名稱時原樣沿用；多項需求屬於同一目標時使用簡短摘要；彼此不同且使用者未命名時使用「<專案名稱> 多需求工作包」。顯示名稱不得取代或合併原始需求。
- 舊工作若已由實際交接路徑指向 `docs/work/<功能名稱>/`，繼續沿用該目錄；不搬移、不改名、不建立重複工作包。
- 不為了儲存或交接執行 `git add`、Commit、Push、建立 Repository 或修改 Git 設定。

## 流程

1. 讀取 `docs/planning/requirements.md`、`docs/planning/architecture.md`、專案指令、`CONTEXT.md`、相關 ADR 與程式庫現況。
2. 依已核准需求的原始順序，為每一項原始需求建立一個不重複的三位數識別碼，從 `R-001` 開始；若來源已有合法且不重複的 `R-xxx` 就原樣沿用。
3. 依下方格式撰寫狀態為「草稿」的規格，不加入未確認內容。
4. 確認唯一工作識別碼、繁體中文顯示名稱與實際工作目錄，再寫入固定路徑。
5. 顯示完整規格與實際路徑，等待使用者核准；修改後更新同一來源，不建立副本。
6. 使用者明確核准且內容自上次顯示後未再變更時，把同一份 Spec 的狀態更新為「已核准」。

## 上游呼叫協定

- 呼叫者識別為 `grill-me` 或 `brownfield-planner` 時，首次呼叫只寫入並回傳草稿 Spec、需求識別碼、實際路徑與工作資料；不得自行假設使用者已核准。
- 上游 Planner 顯示同一份 Spec 並取得使用者核准後，必須以相同呼叫者識別再次呼叫本技能，明確傳入核准結果。
- 第二次呼叫先確認工作識別碼、路徑與內容未被換成其他版本，再只把狀態從「草稿」更新為「已核准」並交回同一個上游 Planner。
- `brownfield-planner` 只可傳入使用者已選定的架構健檢候選與後續已核准架構決策；本技能不得重新加入被拒絕的候選或擴大重構範圍。
- 沒有呼叫者識別的單獨使用模式，仍由本技能顯示 Spec、取得核准並更新同一份文件。

## 規則

- 每項原始需求各占一行，固定使用 `- R-001：原文` 格式；不得把多項需求合成一個識別碼，也不得把一項需求拆成多個識別碼來灌水。
- 已建立的 `R-xxx` 在同一工作中不得重新編號或改配其他需求；新增需求使用下一個未使用編號，移除需求也不得把舊編號改配給別項需求。
- 「草稿」與「已核准」是 Spec 唯一合法狀態；任何內容變更都先回到「草稿」，再次取得使用者核准後才改為「已核准」。
- User Stories 描述誰需要什麼及原因；驗收條件描述怎樣才算完成。
- 使用專案術語並遵守 ADR。
- 寫模組與介面名稱；省略易過期的檔案路徑、行號與大段程式碼。
- 原型已驗證的狀態機、Schema 或型別只保留決策所需片段並標記來源。
- 不實作、不拆 Ticket、不修改來源碼。

## 完成條件

- 規格只包含核准內容。
- 每項原始需求都有唯一且穩定的 `R-xxx`，並以規定格式保存原文。
- User Stories 與驗收條件完整。
- 架構與測試決策可供拆票。
- 工作識別碼、顯示名稱與實際工作目錄已保存，且沒有覆寫既有工作。
- 規格已寫入本機固定路徑。
- 使用者核准規格，且同一份 Spec 的狀態已更新為「已核准」。
